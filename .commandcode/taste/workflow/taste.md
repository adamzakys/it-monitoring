# Workflow & Communication Preferences

- Expects project responses in Bahasa Indonesia. Confidence: 0.9
- When a new design system or style guide is requested, install external specs by saving `SKILL.md` and `DESIGN.md` to `.agents/skills/<name>/` for tool re-indexing. Confidence: 0.8
- Prefers batch-processing UI changes: read all relevant selectors in parallel, then apply glassmorphism/cascading updates in a single pass rather than fixing one component at a time. Confidence: 0.85
- Expects compiled/generated assets to be rebuilt and the actually-served output verified after source edits (e.g. `npm run css:build`, `node --check`, then curl the served stylesheet and grep for the new tokens) — editing source files alone is not proof of a done change. Confidence: 0.7
- Wants immediate bug fixes without fluff; prioritizes getting broken interactive states (like panel toggles) working correctly over theoretical explanations. Confidence: 0.85
- When asking how a feature or data transform actually works (what a displayed metric means, how logs are normalized/converted, where a conversion happens), wants the answer traced down to the real mechanism in the codebase — the actual config/code path with file and line references — plus the equivalent raw execution (e.g. the literal `ping -c 3 -i 0.25 -W 2 <ip>`) and concrete step-by-step timelines — rather than an abstract restatement of the definition. Pushes back on assumptions ("gamungkin dong") and keeps drilling (e.g. whether the UI waits for all samples before rendering) until the concrete sampling/conversion and display behavior is spelled out. Confidence: 0.7
- Prefers to apply production-affecting service changes (e.g. the `sudo kill -HUP` Telegraf reload) himself: the agent should prepare the config and hand over the exact commands rather than restarting/mutating running production services; when verification is needed, spin up an isolated second instance/port and clean it up rather than touching the live one. Confidence: 0.7
- Does not use Docker: for setup/installation guidance expects native, host-level installs (distro packages from the official vendor repo, `systemctl enable --now <service>`) rather than Docker/Docker Compose as the suggested path — "saya gapake docker". Confidence: 0.75
- Runs on Fedora (dnf/RPM); scripts and docs must not assume a Debian/apt environment (e.g. hardcoded `/usr/local/bin/telegraf` or `apt install`), and distro-specific mismatches should be called out with the corrected command. Confidence: 0.6
- Uses fish as his interactive shell: commands handed over for him to paste into his terminal must be fish-compatible, not bash-only. Bash-style redirections (e.g. `>/dev/null` on a continued pipeline) fail with "Expected a string, but found a redirection"; the expected fix is to rewrite them for fish (quote the redirection, use `printf`, or wrap the whole privileged line in `sh -c '...'`). Confidence: 0.8
- Long one-liners pasted into his terminal get mangled (continuations/newlines inserted mid-command), so privileged setup steps should be handed over as a short runnable helper script (e.g. `sudo bash scripts/x.sh`, idempotent, self-validating) or typed one command at a time rather than a long multi-line paste block. Confidence: 0.6
- Runs handed-over setup/helper scripts literally and stops at any interactive prompt: when a script pauses for a value the agent already created or knows (e.g. an admin username/password), he pastes the prompt back asking what to enter. Provide interactive credentials/answers up front or make the step non-interactive/self-filling instead of leaving prompts for him to resolve. Confidence: 0.6
- When onboarding a new app into an existing product ecosystem, expects a paste-ready design-rules contract — an opening prompt plus the full spec — to hand to that app's AI coding session, derived from the existing app's real CSS/tokens rather than an invented design system. Confidence: 0.7
- For documentation/marketing deliverables (e.g. a portfolio write-up), never invent metrics or business claims: audit the real repo/README/docs first and write only claims that are actually true, leave explicit fill-in placeholders (e.g. `[ISI: ...]`) where real numbers are missing, and call out existing repo claims that aren't actually implemented so they aren't reused ("Jangan mengarang metrik", "Jangan mengarang; hanya laporkan yang benar-benar ada di kode/dokumen"). Confidence: 0.85
- Prefers documentation handed over as a Markdown file with embedded screenshot placeholders: each image slot marked in-place (what must be visible, a proposed filename like `01-dashboard-hero.png`, path under `docs/.../images/`) so he can paste the real image later, plus an appendix checklist of every screenshot needed and separate business-facing vs. technical sections. Confidence: 0.75
